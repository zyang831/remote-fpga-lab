# DE25 Nano Step 4: Run Inference on the DLA IP — Guide + Known Issues

Builds on Step 3 (runtime deployed to board). Covers: confirming the
architecture file, compiling a model, flashing the DLA-integrated bitstream,
and the kernel/runtime patches needed to actually exercise the hardware.

Workspace: `$TOP=/home/<user>/coredla_work`, Quartus bitstream project at
`/home/<user>/quartus_projects/CoreDLA_GHRD`, board reachable at
`terasic@board-01` (Tailscale).

**Status: in progress, past the hardware scare.** Everything through
"compile + stage the model" works, and §7 (the `CoreDlaDevice` `numInstances_`
assertion) is now **fixed** — it was a stale devicetree address, not a
Platform Designer/qsys bug as an earlier pass through this concluded (see §7
for the correction). Currently blocked one step further in, at a
`WriteToDDR` assertion (§8) — not yet root-caused.

## 1. Confirm the architecture (.arch) file matches the bitstream

Don't guess which `.arch` was used to build the bitstream — verify it. The
DLA IP's `ARCH_OPTION` parameter is recorded in
`CoreDLA_GHRD/ip/qsys_top/qsys_top_ai_ip_0.ip` (search for `ARCH_OPTION`):
in this project it's `AGX5_Small_NoSoftmax_AGX5`.

`dla_create_ip` auto-appends a device-family suffix to the arch file's
basename when it generates the IP folder. Reproduce it to confirm the match:

```bash
source /opt/intel/openvino_2024/setupvars.sh
source /opt/altera/fpga_ai_suite_2025.3.1/dla/bin/init_env.sh
rm -rf /tmp/test_ip_dir
dla_create_ip --arch /opt/altera/fpga_ai_suite_2025.3.1/dla/example_architectures/AGX5_Small_NoSoftmax.arch \
  --flow create_ip --ip_dir /tmp/test_ip_dir --skip_parameter_rom
find /tmp/test_ip_dir -type d -iname "*AGX5*"
# -> .../verilog/AGX5_Small_NoSoftmax_AGX5   (matches CoreDLA_GHRD exactly)
```

If the folder name matches, that's your `.arch` file. (This only proves the
*filename* matches, not necessarily byte-identical content — worth keeping
in mind if you ever hit a hardware-layout mismatch later, see the bug at the
bottom of this doc.)

## 2. Compile a model

No model ships pre-converted anywhere in this environment. Set up a
throwaway venv matching the host's OpenVINO version (2024.6.0) so IR format
matches what `dla_compiler` expects:

```bash
python3 -m venv $TOP/de25_nano_bringup/model_prep/.venv
$TOP/de25_nano_bringup/model_prep/.venv/bin/pip install "openvino-dev[tensorflow2]==2024.6.0"
```

Download + convert resnet-50-tf (matches the path `run_inference_stream.sh`
already hardcodes, so reuse that expectation):

```bash
cd $TOP/de25_nano_bringup/model_prep
.venv/bin/omz_downloader --name resnet-50-tf -o models
# omz_converter needs the legacy Model Optimizer explicitly pointed at:
.venv/bin/omz_converter --name resnet-50-tf -d models -o models_ir \
  --mo .venv/bin/mo
```

Produces `models_ir/public/resnet-50-tf/FP32/resnet-50-tf.xml` (+ `.bin`).

Compile for the DLA IP. **Two variants needed** — `dla_benchmark` works with
either, but `streaming_inference_app` (what `run_inference_stream.sh`
actually uses) requires the no-folding variant, per the comment already in
that script:

```bash
source /opt/intel/openvino_2024/setupvars.sh
source /opt/altera/fpga_ai_suite_2025.3.1/dla/bin/init_env.sh
cd $TOP/de25_nano_bringup/model_prep

dla_compiler --march /opt/altera/fpga_ai_suite_2025.3.1/dla/example_architectures/AGX5_Small_NoSoftmax.arch \
  --network-file models_ir/public/resnet-50-tf/FP32/resnet-50-tf.xml \
  --foutput-format dla_compiled_result --o compiled/resnet50.bin \
  --fdisplay-device                      # dla_benchmark variant

dla_compiler --march /opt/altera/fpga_ai_suite_2025.3.1/dla/example_architectures/AGX5_Small_NoSoftmax.arch \
  --network-file models_ir/public/resnet-50-tf/FP32/resnet-50-tf.xml \
  --foutput-format dla_compiled_result --ffolding-option 0 \
  --o compiled/resnet50_nofold.bin       # streaming_inference_app variant
```

`--fdisplay-device` output should show `subgraph# 0: FPGA` /
`subgraph# 1: CPU` (2 subgraphs) — confirms the network actually maps onto
the DLA IP rather than falling back entirely to CPU.

## 3. Flash the bitstream to the board's QSPI

This board/GHRD flow programs the FPGA config into onboard QSPI flash via
JTAG at power-on (Active Serial boot, MSEL=001) — **not** a Linux-side
`fpga_manager` `.rbf` load. Confirmed from Terasic's
`DE25_Nano_Demonstration_Manual.pdf` (Ch. 4) and the reference
`SoC_FPGA/GHRD` demo project's `sof_with_hps.bat`/`sof_to_jic.bat`.

`CoreDLA_GHRD/output_files/golden_top_hps_auto.sof` is already the
HPS-handoff-merged `.sof` (auto-generated by the fitter — step 1 of the
reference batch files is done for you). Convert + flash:

```bash
QUARTUS_ROOTDIR=/home/<user>/altera_pro/25.3.1/quartus
cd /home/<user>/quartus_projects/CoreDLA_GHRD/output_files
$QUARTUS_ROOTDIR/bin/quartus_pfg -c golden_top_hps_auto.sof golden_top_hps.jic \
  -o device=MT25QU128 -o flash_loader=A5EB013BB23B -o mode=ASX4
```

This host is a remote lab machine with no physical USB access to the board
— `golden_top_hps.jic` needs to be copied to whoever has hands on the board
(Tailscale hostname `mender-host`, IP `<TAILNET-IP>`) and programmed via
Quartus Programmer there:

- Connect USB-C to the board's "USB Blaster III" JTAG port.
- Confirm SW5 MSEL[2:0] = `001` (this is also the **normal power-on** AS
  boot mode for this board — not just a JTAG-programming-only setting, no
  need to change it back afterward).
- Program + Verify the `.jic` onto the `MT25QU128` flash device (tick both
  checkboxes in Quartus Programmer, or `quartus_pgm -c 1 -m jtag -o
  "pvi;golden_top_hps.jic"` then `-o "v;golden_top_hps.jic"` from the CLI).
- Full power-cycle (not just reset).

## 4. Gotcha — QSPI boot-time config silently stalls at "early user mode"

**This is the one that cost the most time.** After flashing + power-cycling,
`altera-msgdma.ko`'s probe (or any raw register touch into `0x2000_0000+`
fabric address space) triggered a **kernel panic** (`SError` / asynchronous
external abort), not a clean error — the whole board went unresponsive to
ping, needing a physical power cycle to recover.

Root cause, confirmed via serial console + a direct register read (safe,
since System Manager registers are always accessible regardless of bridge
state):

```bash
ssh terasic@board-01 'sudo python3 -c "
import mmap, os, struct
f = os.open(\"/dev/mem\", os.O_RDONLY | os.O_SYNC)
m = mmap.mmap(f, 4096, mmap.MAP_SHARED, mmap.PROT_READ, offset=0x10d12000)
print(hex(struct.unpack(\"<I\", m[0xdc:0xe0])[0]))   # SYSMGR_SOC64_FPGA_CONFIG
"'
```

Reads `0x2` (`EARLY_USERMODE` bit only) instead of `0x3`
(`EARLY_USERMODE | FPGA_COMPLETE`). This board does a **two-stage config**:
stage 1 (I/O ring + HPS pins, needed for LPDDR4 calibration) completes fine
via QSPI/SDM autonomous boot, but stage 2 (the actual core fabric logic —
the whole DLA IP) never finishes. U-Boot's own boot log even catches this
and aborts gracefully (`bridge enable;` in `uboot-script/uboot.txt` prints
`FPGA not ready. Bridge reset aborted!` and skips it) — but nothing warns
you *after* Linux is up, so any code that touches the fabric directly
(a kernel module probe, a raw `/dev/mem` poke) hits unbridged address space
and gets an SError. **Reflashing + reverifying the `.jic` (Program + Verify,
both passed 100%) did not fix this** — it's not a corrupted-flash issue.

**Fix — trigger a runtime FPGA reconfig via Linux's own `fpga_manager`,
using the *same* `.core.rbf` already sitting in
`CoreDLA_GHRD/output_files/`:**

```bash
cat > fpga_full.dts <<'EOF'
/dts-v1/;
/plugin/;
&{/fpga-region} {
	firmware-name = "golden_top.core.rbf";
};
EOF
dtc -@ -O dtb -o fpga_full.dtbo fpga_full.dts

# copy golden_top.core.rbf + fpga_full.dtbo to the board, then on-target:
sudo cp golden_top.core.rbf /lib/firmware/
sudo mkdir -p /sys/kernel/config/device-tree/overlays/fpga_reload
sudo cp fpga_full.dtbo /sys/kernel/config/device-tree/overlays/fpga_reload/dtbo
```

`dmesg` shows `fpga_manager fpga0: writing golden_top.core.rbf to Stratix10
SOC FPGA Manager`, `state` flips to `operating`, and the FPGA_CONFIG
register now reads `0x3`. This goes through the SDM mailbox rather than raw
bus access, so a failure would report cleanly instead of hanging — much
safer to experiment with than re-flashing+power-cycling.

This needs to be redone **every power cycle** (it's a runtime reconfig, not
persisted to QSPI). Worth automating into a systemd unit or rc.local once
the hardware bug below is fixed and this becomes the steady-state flow —
not done yet since inference itself is still blocked.

## 5. Kernel driver gotchas

- **`uio_pdrv_genirq` needs `of_id=generic-uio`** to bind `coredla0` /
  `stream_controller0` / `layout_transform0` (3 UIO devices). Already
  documented in Step 2/3 — `/etc/modprobe.d/coredla-uio.conf` should persist
  this, but **check it's actually there after every reflash/power-cycle** —
  it went missing at least once this session (cause unconfirmed; possibly
  unrelated to this work, but don't assume it survived).
- **`msgdma_userio.ko` isn't in this kernel build.** It's an Altera-provided
  out-of-tree module (`meta-altera-fpga-coredla` Yocto layer, not part of
  the manual Step 2 kernel clone) needed for `/dev/msgdma_coredla0` /
  `/dev/msgdma_stream0`. Source is at
  `/opt/altera/fpga_ai_suite_2025.3.1/dla/hps/ed4/yocto/meta-altera-fpga-coredla/recipes-drivers/msgdma-userio/files/`.
  Build it out-of-tree against the exact kernel source tree used for the
  board (`$TOP/de25_nano_bringup/linux`, which still has `Module.symvers`
  from the Step 2 build):
  ```bash
  mkdir $TOP/de25_nano_bringup/msgdma_userio_module
  cp .../msgdma-userio/files/*.c .../files/*.h $TOP/de25_nano_bringup/msgdma_userio_module/
  # Makefile: obj-m := msgdma_userio.o; msgdma_userio-y += msgdma_userio_platform.o msgdma_userio_chr.o
  make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
    KERNEL_SRC=$TOP/de25_nano_bringup/linux modules
  ```
- **`msgdma_userio.ko` also depends on `CONFIG_ALTERA_MSGDMA`** (the actual
  mSGDMA DMA-engine driver for `altr,socfpga-msgdma`,
  `drivers/dma/altera-msgdma.c`), which Step 2's kernel `.config` never
  enabled. Without it, `msgdma_userio`'s probe fails with `Failed to request
  dma` (`-EPROBE_DEFER`) — harmless-looking, easy to miss. Enable + build:
  ```bash
  cd $TOP/de25_nano_bringup/linux
  export ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-
  scripts/config --module CONFIG_ALTERA_MSGDMA
  make syncconfig     # scripts/config alone does NOT regenerate include/config/auto.conf —
                       # must run this explicitly or the module silently won't build
  make -j$(nproc) M=drivers/dma modules
  ```
  Load order matters: `altera-msgdma.ko` **before** `msgdma_userio.ko`.
- **`/dev/uio*` and `/dev/msgdma_*` are root-only (0600) by default** — no
  udev rule grants the `terasic` user access. `chmod 660` + `chgrp terasic`
  after every load (or add a udev rule if this becomes permanent).

## 6. Runtime software gotchas

- **`plugins.xml` hardcodes `libopenvino_intel_cpu_plugin.so`** (x86 naming)
  but the cross-built ARM target ships `libopenvino_arm_cpu_plugin.so`.
  `dla_benchmark` fails with `Cannot load library
  'libopenvino_intel_cpu_plugin.so'` otherwise. `dla_benchmark` accepts a
  `-plugins <path>` override; `streaming_inference_app` does **not** (no
  such flag exists — checked `--help`), so for the streaming app you must
  edit `~/app/plugins.xml` in place. This should really be fixed at the
  source (`runtime/plugins.xml`) for future HPS builds rather than patched
  per-deployment.
- **Both `dla_benchmark` and `streaming_inference_app` require
  `COREDLA_ROOT`** set on-target (e.g. `export
  COREDLA_ROOT=/home/terasic/app`) — not documented in either script,
  fails with a plain env-var error otherwise.
- **`run_inference_stream.sh` has a non-POSIX `>&` redirect** (`killall -9
  rngd >& /dev/null`) — fails with `Syntax error: Bad fd number` under
  `/bin/sh` (dash on this rootfs), despite the `#!/bin/sh` shebang. Needs
  `> /dev/null 2>&1` instead. Worth fixing in the source script.
- **Watch scp for silent truncation on large files.** The compiled model is
  ~150MB; one transfer silently truncated to ~80MB with no error from `scp`
  itself, surfacing later as a confusing OpenVINO deserialization error
  (`String size is greater than the number of bytes remaining in the
  stream`). Always verify `ls -la` size matches on both ends after copying
  the `.bin`.

## 7. Fixed bug — coredla0 devicetree address was wrong (not a hardware bug)

Both `dla_benchmark` and `streaming_inference_app` initially failed
identically at device init:

```
CoreDlaDevice::CoreDlaDevice(uint32_t, bool): Assertion `numInstances_ >= 1' failed.
```

`CoreDlaDevice`'s constructor (`runtime/coredla_device/src/coredla_device.cpp:97`)
probes for live DLA instances by writing a mask to the interrupt-control CSR
(offset `0x200`) and reading back the interrupt-mask CSR (offset `0x204`);
if the readback doesn't match, it assumes 0 instances.

**An earlier pass through this misdiagnosed it as a qsys/Platform Designer
hardware bug** (raw `/dev/mem` probing at `0x20014000`, the address the
devicetree claimed for `coredla0`, showed only ~4 address bits decoding —
looked exactly like a too-narrow CSR slave connection). That conclusion was
wrong. The real cause: **`0x20014000` was simply the wrong address.**

Platform Designer's own exported address map
(`CoreDLA_GHRD/qsys_topaddress_map.amap`/`.csv` — Export → Address Map)
shows `dla.csr_axi` actually sits at offset `0x0002_0000` within the
`subsys_hps.lwhps2fpga` bridge window, range `0x800` — matching the IP's
own declared `C_CSR_AXI_ADDR_WIDTH = 11` (2KB,
`dla_top_wrapper_AGX5_Small_NoSoftmax_AGX5.sv:26`, confirming the IP itself
was never the problem). Since every other DLA peripheral's devicetree
address confirms `lwhps2fpga`'s HPS-side physical base is `0x20000000`
(`stream_controller0@20010000`, `layout_transform0@20002000`,
`msgdma@20000000`/`20001000`), the real physical address is **`0x20020000`**,
not `0x20014000`. This board has a pre-existing Terasic peripheral
(`subsys_periph.pb_cpu_0_s0`, the Nios V temp/power/fan monitor from the
base GHRD) occupying `0x0`-`0x1ffff` in that same bridge window, ahead of
where the DLA IP landed — the generic FPGA AI Suite devicetree patch
(`coredla-agilex5-dts.patch`, applied in Step 2 §3) doesn't know about that
and assumes a default offset that's only correct when the DLA IP is the
*only* thing in the window. Full detail + the fix now in
`STEP2_BSP_BUILD_GUIDE.md` §3 (search "Confirmed bug").

**Verify before trusting `0x20014000` vs `0x20020000` on any other build** —
these are specific to this board's qsys layout, re-derive from your own
`Export Address Map` output if anything about the design changes.

**Fix applied:** edited
`arch/arm64/boot/dts/intel/socfpga_agilex5.dtsi`, changed the `coredla0`
node's `reg` from `<0x20014000 0x00000400>` to `<0x20020000 0x00000800>`,
rebuilt just the dtb (`make dtbs`, seconds — no full kernel/U-Boot/bitstream
rebuild needed), and replaced `socfpga_agilex5_de25_nano.dtb` on the board's
boot FAT partition (`/dev/mmcblk0p1`, mount + `cp` + `sync` + `umount`).
After reboot, `dla_benchmark` now gets past the `numInstances_` assertion
cleanly.

**Remember**: after every power cycle, the runtime FPGA reconfig (§4) and
UIO/msgdma module reload (§5) both need redoing before this works — neither
persists across reboots yet.

## 8. Current blocker — WriteToDDR assertion (not yet root-caused)

With §7 fixed, `dla_benchmark` now gets one step further before failing:

```
MmdWrapper::WriteToDDR(int, uint64_t, uint64_t, const void*) const: Assertion `status == 0' failed.
```

This is a different code path — `dla_mmd_ddr_write` →
`mmd_device::write_block` (`HPS_MMD_MEMORY_HANDLE` branch) → `_spDmaDevice`,
which routes through `/dev/msgdma_coredla0` (ioctl/write-based, not a raw
CSR mmap) rather than the UIO CSR region that was the problem in §7. No
descriptive error printed before the assert — not yet traced further.
Worth checking first: whether `dla.ddr_axi`'s actual address/window (routed
via `address_span_extender_axi_256_0`, per the same `.amap` export used in
§7) matches what `dma_device.cpp`/`mmd_device.cpp` assume, same class of bug
as §7 but on the DDR data path instead of the CSR control path.

## 9. Once fully working: staging + running inference

```bash
# from this host, after re-flash + reconfig (§3-4) + dtb fix (§7):
scp compiled/resnet50.bin compiled/resnet50_nofold.bin \
    /opt/altera/fpga_ai_suite_2025.3.1/dla/example_architectures/AGX5_Small_NoSoftmax.arch \
    terasic@board-01:~/app/resnet-50-tf/
# VERIFY sizes match after transfer (§6) before trusting the result.

# on-target, dla_benchmark path:
cd ~/app
export COREDLA_ROOT=/home/terasic/app
./dla_benchmark.sh -cm resnet-50-tf/resnet50.bin \
  -arch_file resnet-50-tf/AGX5_Small_NoSoftmax.arch \
  -plugins ./plugins_arm.xml -i resnet-50-tf/images \
  -d HETERO:FPGA,CPU -niter 8 -api sync

# or the streaming path (needs the plugins.xml + POSIX + COREDLA_ROOT
# fixes from §6 applied to run_inference_stream.sh first):
./run_inference_stream.sh
```

Success looks like a real classification result (top-1 class + confidence)
printed per image, not an error — that's the actual "inference runs
end-to-end" milestone, still pending the §8 fix above.
